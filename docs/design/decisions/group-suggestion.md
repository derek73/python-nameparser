## Log

- **2026-11-10 SCOPE — THE NEVER-DETECT-LANGUAGE RULE IS ABOUT THE PARSE, AND THE GROUP SUGGESTER IS OUTSIDE IT (PROPOSED, FOR REVIEW).** AGENTS.md's design philosophy says the parser never detects language, because the language of a Latin-script name cannot be read off the name. `Parser.suggest` works on a group the caller declares to share one convention, reads statistics over the group and returns configuration with the evidence behind it, which the caller applies; it never mutates a base `Parser` or a default and changes no parse. Proposed wording: "the parser never detects language; the group suggester may, says what it saw, and its answer is configuration the caller applies". The given-name table does not ask what language a name is; it asks whether a word is almost always a given name, anywhere. This entry is the first commit of the branch so the wording can be settled before the code is read; the only items recorded as decided are the two under TABLES (the private tables, the nam_dict approval); the rest of this file is proposed, for review.
- **2026-11-10 TABLES — TWO PRIVATE COMPILED TABLES, READ BY THE SUGGESTER ONLY.** The romanized surnames (zh, ko, vi) and the common given names are written by tools under `tools/vocab/`, like `familiar.py`, into committed private modules under `nameparser/config/`, with a test that each is current. They are not `Lexicon` kinds for the first version, because a `family` reading on `Lee`, `Song` or `Long` would move the suffix gates derived from name readings and a `given` reading would move titles and particles; a table no parse reads moves no snapshot. Making them `Lexicon` kinds later, if a caller needs to tune them, stays open. The given-name table is derived from nam_dict's 55 country columns (top N per country by frequency band, unioned), keeping a name only if ORCID's researchers wrote it in the family box at most 5% of the times they wrote it (at least 20 uses), it is longer than one letter and it is not in the romanized surname sets; N and the threshold are tuned against the measurement populations. Licences: nam_dict GNU FDL 1.2, ORCID's public data file CC0, Unihan the Unicode licence; the module header carries the sources once. The table derived from nam_dict is approved.
- **2026-11-10 SIGNALS — WHAT EACH SIGNAL VOTES, AS MEASURED WITH THE THROWAWAY SPIKES.** Measured with the throwaway spikes; re-taken by tools/differential/suggest_measure.py in this PR. Populations are PatentsView inventors by country, UK company filers (PSC) by nationality, Czech candidates, Vietnamese names and national parliament lists (OpenSanctions); none of them built the given-name list.
  - Capitals word position: decisive where present (Turkey's parliament `Mehmet DEMİR` 592:0); a capitals run in the middle (Hong Kong `Jeffrey LAM Kin-fung`) does not vote.
  - Comma names do not vote on order: 373 comma names outvoted the comma-less majority of India's Lok Sabha list.
  - Trailing initial (`Smith J.`) votes family-first; a leading initial does not, having voted 76 wrong of 112 in given-first Indian groups (`S. Ramesh`).
  - Romanized zh, ko and vi surnames: groups of CN, TW, KR and VI names 99-100% right from 5 names in both orders, about 97% of names voting right; one-letter words are excluded, the spike's set having swallowed initials (`A.` folds to pinyin `a`).
  - Common given names, per name where it votes: 98-99% right in most groups (Czech, Polish, British, Spanish, German, Italian, Japanese, Russian, US) and 90-95% in Indian, Nigerian and Romanian ones. Family-first groups' share right, before and with the top-500 list: Japanese (PatentsView) 12% to 88% at 5 names and 55% to 100% at 50; Turkish (PSC) 13% to 78% and 66% to 100%; Indian (PSC) 10% to 35% and 31% to 87%; Polish, Spanish, Italian and Czech 71-83% to 96-100% at 5 names and 100% at 50. Given-first groups stay at 95-100%. Top 100 per country gives 2,375 names, top 500 gives 4,267.
  - Patronymic presence: the spike's position vote got Ukraine's Rada 1,582:0 right on order, but order is the wrong answer for an East Slavic group. Measured on the tree (master 01b982e3 plus #1304): with `{EAST_SLAVIC}` under the default order `Sidorov Ivan Petrovich` and `Ivan Petrovich Sidorov` both read given Ivan, family Sidorov, patronymic Petrovich, and under `FAMILY_FIRST` the given-first `Ivan Petrovich Sidorov` reads given Petrovich, family Ivan with no patronymic. So an East Slavic group gets the rule alone (what `locales.RU` ships) and the patronymic does not vote on order; the Turkic combination is measured on the Azerbaijani, Kazakh, Uzbek and Turkmen lists before it is picked, and stays out of the first version if none reads them right.
- **2026-11-10 DECLINED — EVIDENCE THE SUGGESTER DOES NOT USE.**
  - Declined: the vocabulary's `given` and `family` readings as order evidence. Measured with the throwaway spikes, they vote wrong about as often as right and mostly wrong in family-first groups (Dutch 92 right, 496 wrong): they are collision words, chosen because they clash with a title or particle, not common names.
  - Declined: `Reading.languages` as evidence for suggesting a language pack. English and the Spanish given-name list top nearly every group, Cyrillic groups carry no tags and Portugal's parliament ranks the Spanish list over `pt`. A pack could later follow from settings evidence; it is out of the first version.
  - Declined, superseded: the familiar forms. They were useful (Western family-first groups 93-100% from 10 names once the romanized surnames were subtracted, `Kim`, `Lee` and `Chan` being listed familiar forms), but the common-given-names list alone does as well or better, and it keeps the parse's `familiar` vocabulary out of this.
- **2026-11-10 TURKIC — THE RULE ALONE, NO ORDER OF ITS OWN (proposed, for review).** Measured on the OpenSanctions parliament lists, read from `~/.cache/nameparser-tools/local/opensanctions-parliaments/raw.jsonl` line by line, keeping the rows whose `form` is `"name"` and whose `script` is `Latin` or `Cyrillic` (the dataset keys named below). The `script` field also holds `mixed` on four rows (one in `uz_legislative_chamber`'s `Firdavs Qobiljonovich Qurbоnov`, one more there, one in `uz_senate`, one in `kz_senate`): a name written with a Cyrillic letter inside a Latin word, a lookalike typo, which no real reader sees as another script, so they are dropped and not scored. Lists: Latin `az_parliament` 124, `kz_senate` 48, `uz_senate` 59, `uz_legislative_chamber` 143, `tm_mejlis` 124, Cyrillic `kz_mazhilis` 96, `kg_jogorku_kenesh` 90. Scoring: a name is right when `parsed.family` is the true family. Where the list writes the family in capitals (`az_parliament`, `kz_mazhilis`) the one capitals word is the true family; elsewhere the family is the end the list writes it at, read by eye off the first twelve names of each list in file order (after the filter above), then applied to every name of two or more words (kz_senate and uz_senate first, uz_legislative_chamber, tm_mejlis and kg_jogorku_kenesh last). So only `az_parliament` and `kz_mazhilis` have an independent truth; every other row is scored against the list's own convention (the end that list writes the family at), not against a sampled reading of each name, and it shows what the settings do to a list written that way, not how often they read real families. The by-eye sample is twelve, not the thirty first planned. Re-taken by tools/differential/suggest_measure.py when it lands.   Only 121 of az's 124 names, 2 of uz_senate's, 7 of uz_legislative_chamber's, 2 of tm_mejlis's and 4 of kg_jogorku_kenesh's carry a Turkic marker word (`oglu`, `oğlu`, `qızı`, `o‘g‘li`); the other lists write Russified `-ovich` patronymics, which are East Slavic votes, and no Turkic setting touches them. The order columns are the list's own convention, so FF raises the family-first lists and breaks the family-last ones whether or not the rule is on: the order is not a property of the patronymic. What the rule adds is that `{TURKIC}` alone reads a marker name either way round under the default order (`Mamedov Ali Huseyn oglu` and `Ali Huseyn oglu Mamedov` both family Mamedov, given Ali, patronymic `Huseyn oglu`), where the default alone leaves family `oglu`; under `FAMILY_FIRST` the given-first `Ali Huseyn oglu Mamedov` reads family Ali. So the spec's builder check, that TURKIC under the default order leaves family `oglu`, no longer holds on the tree measured here (the rule reads both) and the Turkic answer is the East Slavic one minus the forced order: a decided Turkic rule gives `patronymic_rules={TURKIC}`, and the order is decided from the names' own votes, never forced to given-first, because forcing it would turn az's capitals-written family-first names (124/124 with the order decided, 121/124 with it forced) wrong. End to end through `Parser().suggest` on each whole list: az 124/124 (`name_order=FAMILY_FIRST` from the capitals votes, `{TURKIC}`), the Russified lists decided `{EAST_SLAVIC}`. Known cost: where a list holds both shapes the larger set wins the one patronymic decision, so uz_senate (2 marker names against `-ovich`) decides East Slavic and reads 52/59 (its `o‘g‘li` names, and its two-word names, which the forced given-first order of a decided East Slavic rule reads family-last); kz_senate's `-uly` patronymics (`Kydyrali Darkhan Kuandykuly`) are not a Turkic signal at all and read 41/48, still above "nothing" at 0/48. Both are about East Slavic deciding a mixed group, not the Turkic answer, and are left open.
