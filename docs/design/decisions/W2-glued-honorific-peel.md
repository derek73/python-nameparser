- 2026-08 #312 — the peel crosses the family comma and the 间隔号: both answer where a name DIVIDES into surname and given, a question the peel never asks. Provenance matters here: neither gate was argued for the peel specifically — both came with the placement (#312's own framing) — so the crossing was a repair of inherited gates, not a designed-in property.

- 2026-10-18 (vocabulary phase 1, decisions/vocabulary-model) — RECORDED HERE from the #307/#308 vetting note in nameparser/config/suffixes.py, which the move of the vocabulary to TOML retired; its per-word facts went to each word's TOML entry (`uv run python tools/vocab/query.py --issue 308`). Three class-level points had no other home. The spaced and glued bars are different, and an entry can be safe spaced and unsafe glued, never the other way round, because the spaced position is a token boundary its writer drew. A Han, kana or hangul entry is self-selecting, like the Korean surnames: it can only ever match CJK text. And kana is no license by itself: hiragana spells Japanese GIVEN names (高橋みなみ, pinned in the case table), which is why さん, さま, くん and ちゃん were vetted one at a time as never name-final rather than waved through as kana. Further spaced candidates (여사, 太太) wait on the same case-by-case argument.
- 2026-10-19 #760 — MOVED FROM the peel's code comment in `_script_segment.py` (`_peel_honorific_tail`), the facts the #312/#319 entries above and AGENTS.md's script paragraph did not hold (that paragraph keeps why the run predicate is not the token predicate's plural, and what `lenient_comma_suffixes=False` does here); parses re-run 2026-10-19. WHY ONLY THE FAMILY COMMA CROSSES: a comma is how a writer says which runs are the name, and a family comma is the one structure that splits the name itself across two of them (`김, 민준씨` is runs (0,) and (1,)), with the honorific as often glued to the given side as to the family. Every other structure keeps the whole name in segments[0], so the asymmetry is the point rather than an accident of two cases. "The rest is post-nominals" is true of the SUFFIX comma only: under NO_COMMA segment returns one run and a trailing post-nominal is INSIDE it (`김민준씨 Jr.` is one run of two tokens, family '김', suffix '씨 Jr.'), which is why the scan-back steps over such a token rather than never reaching it. WHY THE RUN PREDICATE IS ASKED: the structure says nothing about whether segments[1] is name text — segment hands every comma form over as FAMILY_COMMA (#613), and a one-word part turned a wholly suffix-shaped remainder into FAMILY_COMMA anyway (`田中さん, V.`). THE SCOPE HOLDS OFF A JUNK TAIL past the second run: `Dr 김민준씨, Jr., 박씨` is a postnominal part behind a whole name (`_postnominal_behind_a_whole_name`), so the scan stays in segments[0] and 박씨 in a third run is never reached (family '김', suffix '씨, Jr., 박씨'). AN EMPTY SECOND RUN stays in scope and contributes nothing: `is_wholly_suffix` is False on it by its own contract (v1 read `Doe,, Jr.` as a family comma), which is the reading the peel wants, flattening an empty run adding no site. FLATTENING SEGMENTS, NOT `state.tokens`, is load-bearing: extracted nickname and maiden content is in tokens but in no segment, and scanning tokens would put the site on a nickname (`김민준씨 (Jimmy)` would peel nothing); the case row `ko_honorific_glued_given_nickname` pins it (family '김', given '민준', suffix '씨', nickname 'Jimmy'). WHY THE PREDICATE IS CIRCULAR HERE ALONE, and so needs the second condition: not because `_comma.decide` asks it too (at group's head, after this stage), but because decide SPENDS the answer differently — it reads the run's shape and stops, the answer being the structure, while the peel reads the same shape and then decides whether to strip the very honorific that produced it. Declining a run that holds the only site does not fall back to another site; it loses the peel outright, and with it the given name, which lands in suffix (`이, J.씨` would read suffix 'J.씨'). DROPPED AS STALE, not moved: the comment said the declined credential lands "`PhD` a title"; it is a suffix (`田中さん, PhD` → suffix 'さん, PhD', rules/W3's example line), as AGENTS.md's script paragraph already says.
