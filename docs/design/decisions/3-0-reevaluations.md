## Standing

- 3.0 carries no v1 compatibility layer: `HumanName`, `nameparser.parser`, `nameparser.util`, `nameparser.config`'s five shim names and the five 1.x word-list names 2.2 retired are gone, so every surface speaks `given` and `family`, a configuration is a `Lexicon` and a `Policy` handed to a `Parser`, and a pickle is a core type's — 2026-10-28 #357, REMOVAL.
- Render's default format space-joins its fields as v1's did, so an interpunct transcription renders space-joined (`str(parse("威廉·莎士比亚"))` is `'威廉 莎士比亚'`) and a caller reinstates the dot with a format of their own; 3.0's render defaults are a clean slate — 2026-08-15.

- Pickle-guard layout breaks landing in a minor release are shim-era friction; the guarded raise stands on its own — 2026-08-15.
- Reading positionally where no script licenses family-first is the safe direction on its own, family-first being the marked case that needs affirmative evidence — 2026-08-15.
- From 2.8, the last 2.x feature release, the uses 3.0 removes warn with a `DeprecationWarning` on every call at the caller's line naming code that runs: constructing `HumanName` or a `Constants`, loading either from a pickle, mutating the shared `CONSTANTS`, and reading `nameparser.config`'s three managers or `nameparser.util.lc`; importing `nameparser`, `nameparser.parser` or `HumanName` stays quiet, and so does reading the shared `CONSTANTS`, which no warning reaches — 2026-10-28 #925 (Derek), WARNINGS.; 3.0 removes those uses and their warnings with them — 2026-10-28 #357, REMOVAL.
- The 3.0 core API — `parse`, `Parser`, `Lexicon`, `Policy`, `Locale` and `ParsedName` — is frozen except for additions, so anything 3.0 later breaks there is a new decision needing its own 2.x warning — 2026-10-28 #925 (Derek), THE CORE API.
- 3.0 keeps no shared configuration, so the contextvars override once parked for it (`with nameparser.config.use(c):`) is not built: it existed to scope the shared `CONSTANTS`, and a parse's configuration is now the `Parser` it runs on — 2026-10-28 #357, REMOVAL.
- An explicit family comma beats script for Latin text, a doctrine inherited from v1 that stands on its own; for CJK script it is a description, not a promise (Elsewhere, below) — 2026-08-15.
- Particle vocabulary is language judgement wearing a position heuristic, so a caller who knows a tradition should be able to opt into a tuned set, which needs packs to carry vocabulary overrides and not only additions; 3.0 work — 2026-08-17.
- Which single-letter connectives read as initials differs by language, a per-word policy that `conjunctions_ambiguous` carries without packs (`e` and `i`); a pack can add a member, so an `nl` pack could mark `y`, and cannot remove one (the next line) — 2026-08-18; 2026-09-20 #397.
- A locale pack's vocabulary is unioned onto the base and can remove nothing, so a caller removing a base entry, such as `e` from `conjunctions_ambiguous` for Portuguese, does it by hand; accepted for 2.x and part of 3.0's pack design — 2026-09-13, SHOULD A LOCALE PACK.

- (A) 2026-08-18 — LOCALE CONTROL OF P3's SINGLE-LETTER CARVE-OUT, and the sharper requirement it puts on the entry above: a pack would have to carry per-word POLICY, not just membership. Which single letters a tradition wants joined differs by language — Spanish writes "y" and would want "e" read as an initial, Portuguese wants the reverse, Dutch would want every single letter read as an initial. One global rule serves all three today: a single ALPHABETIC character in a name of fewer than four pieces stays a name word, and a bare Latin capital never joins (#383). It is v1's Google Code issue 11 fix ("john e smith") generalized to a vocabulary v1 did not have — the set now holds six single-letter conjunctions (y, e, и, і, й, و), and the carve-out reaches all of them because it counts characters, while the capital veto reaches only the Latin ones because it tests a Latin shape. That asymmetry is the visible seam and it is why #383 is open. A pack that could only ADD or REPLACE vocabulary could not express any of it; the join threshold and the initial veto would have to be per-word, per-pack values. Measured while documenting P3: "&" is single-character but not a letter, so it joins at any length ("Juan & Garcia" is one part while "Juan y Garcia" is three).

- 2026-10-28 #925 (Derek), WARNINGS — 2.8 WARNS WHERE CODE USES WHAT 3.0 REMOVES, and is the last 2.x feature release; after it master is 3.0 development and 2.x takes fixes only. SUPERSEDES: the 2026-08-29 entry's removal candidacy for `force_mixed_case_capitalization` (last paragraph). This keeps the 2.0 RFC's promise that a `HumanName` construction warning ships in a 2.x minor before 3.0 (docs/design/nameparser-2.0-rfc.md), which no release had kept: until 2.8 a caller who never mutated the shared `CONSTANTS` was never warned. What warns, and how:
  - Constructing `HumanName` (a subclass included) and a caller-built `Constants`, `Constants.copy()` included; the import-time `CONSTANTS` singleton is built past `__init__`, so `import nameparser` never warns. The cost of exempting it: reading the shared `CONSTANTS` (`'dr' in CONSTANTS.titles`) warns nowhere, so code that only reads it passes `-W error::DeprecationWarning` on 2.8 and breaks in 3.0; docs/migrate.rst says so.
  - Loading a `HumanName` or `Constants` pickle, from `__setstate__`, since unpickling skips `__init__` and the load is the one use construction never sees; each names what to store instead (`parse(text).as_dict()` or the text; a pickled `Parser`). `copy.copy` and `copy.deepcopy` go through the same hooks, a subclass's own included, with only the load warning filtered, a copy being no load; `copy.copy(CONSTANTS)` stays quiet with them, and a `HumanName` built on the copy warns.
  - Reading `SetManager`, `TupleManager` or `RegexTupleManager` from `nameparser.config`, and `lc` from `nameparser.util`, through a PEP 562 `__getattr__`: construction cannot reach a caller who only imports them. The library's own reads go through the private names and stay quiet. `from nameparser.config import *` warns for the three managers its `__all__` names, and `from nameparser.util import *` for `lc`, a cost recorded rather than designed around: dropping the names from `__all__` would remove them from a star import unwarned.
  - Importing `nameparser.HumanName`, `nameparser.parser` and `from nameparser import *` stays quiet (the inventory's A2 and A3): construction catches every real use, and a warning on the name would reach star-importers who never construct one.
  - The shared-`CONSTANTS` mutation message drops the private `Constants` it offered as an escape, which 3.0 removes too, and names `Parser(lexicon=Lexicon.default().add(titles={'dean'}))`; the hook-override message (#280) adds that `HumanName` is removed in 3.0.
  Every warning is a `DeprecationWarning` rather than a `FutureWarning`, emitted on every call at the caller's line and never once per process (a process flag lets a dependency's first `HumanName` consume the warning meant for the caller, the reason the 2026-08-15 bridge template warns per read location, and turns this suite's `filterwarnings = error` into an order-dependent failure under `--dist worksteal`). A `DeprecationWarning` is hidden by default outside `__main__`, so the release log, README and docs/migrate.rst announce the removal loudly instead. Every message names code that type-checks and runs, pinned by tests/v2/test_deprecations.py. `force_mixed_case_capitalization`, a removal candidate since 2026-08-29, is a `Constants` attribute, so removing `Constants` removes it and the construction warning is its removal warning; that follows from the facade's removal rather than being decided apart from it. Phase 4's output model is announced in one line of docs/migrate.rst ("details with the 3.0 alphas"), nothing undecided listed.
