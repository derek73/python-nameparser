# RFC: the vocabulary model and language packs

Status: **design overview**, written 2026-10-19 after phase 1 shipped. It says where the vocabulary model is going and why, phase by phase. It is not the record: each decision is logged in [decisions/vocabulary-model](decisions/vocabulary-model.md) when it is made, and where the two differ, that entry is right and this document is stale. Each later phase gets its own design when it starts, under its issue; this overview is amended as they land. Work is tracked in #747.

For editing the vocabulary as it is today, read [nameparser/vocab/README.md](../../nameparser/vocab/README.md) instead.

## The short version

nameparser recognizes words by vocabulary: titles, suffixes, particles, conjunctions, bound given names, maiden markers. Until 2.6 that vocabulary was a set of base sets plus marker subsets (`particles` and `particles_ambiguous`, `suffix_acronyms` and `suffix_acronyms_ambiguous`, ...). The model replaces the sets with a description of each **word** by its **readings**: what the word can be in a name, and the properties of each reading.

```toml
[[word]]
text = "do"
family = { us_census_2010 = 30301, wikidata = 100, as_of = 2026-10-25 }
given = { us_ssa = 11, wikidata = 9, as_of = 2026-10-25, note = "male births only; Wikidata is a lower bound" }
credential = { expands = "Doctor of Osteopathic Medicine" }
[word.preposition]
expands = "of the, masc. sg."
```

`do` is a credential and a particle, and Vietnamese Đỗ makes it a surname too: its name readings, with the counts they rest on, are what mark both clashes (an entry spread over two files in the shipped data, `en.toml` and `pt.toml`). Under the sets that clash was visible only as an overlap between two of them; as readings it is written on the word. Once every word says which language's names it occurs in, choosing a language can settle the clashes that exist only because the default serves every language.

Four phases, in a fixed order:

| Phase | What | Changes parsing? | State |
|---|---|---|---|
| 1 | The per-word TOML format, compiled to today's sets | no | shipped in 2.6 (#737, #744); #749–#751 gave the words in `und.toml` their languages, leaving two particles of unrecorded origin |
| 2 | Ambiguity derived from clashing readings; the ambiguity gate extended to every reading kind | yes, the first phase that does | #752, design agreed 2026-10-23; 2a, the two name-clash markers derived, landed without moving a parse (decisions/vocabulary-model, 2026-10-25) |
| 3 | Language packs that prefer or restrict their language | yes, for callers who choose one | #753, for 3.0, needs 1 and 2; design agreed 2026-10-28, 3g's connective open; 3a, the reading index and the shared compiler, 3b, the choice on `Locale.languages`, and 3c, the pack-shaped exclusions as readings off by default, landed without moving a default parse (decisions/vocabulary-model, 2026-10-29) |
| 4 | Order and shape; the rules a pack can choose; the output model | yes | #754, 3.0 work; its output model agreed 2026-10-28, ahead of or alongside phase 3's mechanism; 4a to 4d, the reading and the views `generation`, `credentials`, `patronymic` and `surname2`, landed without moving a parse, 4e, the render defaults and `ParsedName.order`, moved the default `str()`, and 4f, `[rules]` compiled into a pack's policy patch, moved no parse (decisions/vocabulary-model, decisions/R6 and decisions/R8 to R10, 2026-10-29) |

Two commitments hold through all four. **The default loads every language and keeps working for names of any language, as today**; choosing a language narrows it (decision 5 in decisions/vocabulary-model). And **languages own vocabulary and defaults, the core owns structure**: a pack configures rules the core implements, and never ships code (mechanisms.md#LOCALE-PACKS-PURE-DATA).

## Why readings, not sets

The sets failed as a model in five ways (decisions/vocabulary-model's preamble has the detail):

- "Ambiguous" meant three things by field: may be a given name (particles), may be a surname (acronyms), may be an initial (conjunctions). Two other marker sets (`honorific_tails`, `given_name_titles`) were not ambiguities at all.
- The direction flipped between layers: `config/` listed the never-given particles, `Lexicon` the may-be-given ones.
- Every marked word was written twice, and the checks on the pairs were uneven.
- A clash between categories was recorded nowhere, and nothing told an author whether an overlap they created was intended (`titles ∩ particles` holds `freiherr` and `st` on purpose) or forbidden (a post-nominal both an acronym and a word).
- A set cannot say which language a word belongs to, which is what a language pack needs.

A reading fixes each of these by construction: a property cannot exist without its reading, so the subset checks disappear; a clash is a word with two readings; and the file a word sits in is its language.

## Phase 1: the format (shipped)

Phase 1 re-encoded the vocabulary and changed no parse. One TOML file per BCP 47 tag holds the words found in names written in that language (`und` for words not yet assigned one, `mul` for words shared on purpose); each `[[word]]` lists its readings keyed by kind; `tools/vocab/build.py` compiles the files into today's sets, and the parser never reads the TOML. The suffix category is classified into six kinds (generation, credential, honorific, professional honorific, status, courtesy); every other category carries its generic kind until its classification issue lands. Exclusions are data: a refused reading is recorded on the word with its reason, and the build refuses it in any file, quoting that reason.

Two choices in phase 1 set up phase 2 and are worth knowing before reading it:

- **The marker sets were explicit flags** (`may_be_given`, `may_be_name`, `may_be_initial`), not derived from name readings, recording past curation rather than evidence. Phase 2a (2026-10-25) derived the two that record a clash with a name, `may_be_name` and `may_be_given`, from name readings, each with dated counts or a `note` where no source counts the word (`te`, `tho` and `du`, once thought to have none, have SSA counts), keeping `may_be_initial` as a property (decisions/vocabulary-model).
- **Names a later phase will use are build errors** (phase 1 reserved `default`, `prefer`, `strict`, `bare_only`, `leading_only`, `trailing_only`, `attaches`, `separators`, and the values `addresses = "full"` or `"any"`), so nothing reads as working before it does. Phase 2h (2026-10-25) gave `default = false` its meaning, a reading recorded that compiles to nothing, and named the phase each of the others waits for; phase 2i gave `attaches` its meaning, the phrase partner below.

The reference for the format is nameparser/vocab/README.md; the decisions behind it, with what was declined and measured, are decisions/vocabulary-model's 2026-10-18 entry.

## Phase 2: derived ambiguity and a general gate

Phase 2 is the first phase that changes how names are parsed. Its design was agreed on 2026-10-23 (#752); the decisions, the evidence for each and the options declined are decisions/vocabulary-model's entry of that date. What follows is the design as agreed. Every sub-phase below had landed by 2026-10-27, when #752 closed; the title words 2j did not reach are #913's.

### Three sources of readings

Every clash the parser decides is between readings of one token, and phase 2 puts them in one pool:

- **Vocabulary readings**, the TOML kinds: titles, suffixes, particles, conjunctions, bound given names, birth markers.
- **Declared name readings**, `given` and `family`, written by hand on a word some file claims or refuses (decision 11), with dated counts as provenance that never compute a reading (decision 12). Nobody maintains surname lists.
- **Shape readings**, which today are rules standing around the vocabulary: the initial ([rules/T4](rules/T4-bare-letter-as-an-initial.md), a bare letter as an initial; [rules/T5](rules/T5-written-shape-of-an-initial.md), the written shape of an initial), the leading abbreviation title ([rules/H2](rules/H2-leading-abbreviation-title.md)), the dotted acronym ([rules/S3](rules/S3-credentials-written-in-joined-chunks.md)), the capitals acronym ([rules/S9](rules/S9-unlisted-words-that-join-the-ambiguous-class-by-shape.md), unlisted words that join the ambiguous class by shape), the roman numeral past the listed ones ([rules/S10](rules/S10-trailing-roman-numeral.md)), paired initials ([rules/C5](rules/C5-paired-initials-after-the-comma.md), paired initials after the comma), and the joined and split spellings of a credential that phase 2 adds.

Shape readings join the pool because of decision 20, which lets a pack's preferred reading outrank a shape-derived one, and which phase 2 applies in the default as well (an abbreviated given name over the leading-abbreviation title, below): a reading can outrank a shape-derived one only if the shape's answer is a reading the gate weighs, not a verdict already written into a tag. Settling a clash by rewriting a tag also erases the word's other readings: retagging a capitals `DO` as an unambiguous credential let its particle reading take it into the family (`Doe, John DO`), which is why the case cue for credentials (#785) waited for the pool. Phase 2g (2026-10-25) settles it where each site chooses a reading, the word keeping its tags ([rules/S6](rules/S6-case-signal-at-the-suffix-slot.md)).

### Ambiguity from readings

A **clash** is a token whose readings would put it in different fields. The two markers that are clashes with a NAME become derived:

- an acronym that may be a name is a word with a credential reading and a `given` or `family` reading;
- a particle that may be a given name is a word with a particle reading and a `given` reading.

The swap is snapshot-neutral by construction once the missing name readings are written, because no word sits in one marker set while needing to stay out of the other (decisions/vocabulary-model, 2026-10-18, with the recompute). The missing readings are declared on the flagged words, a few of them without a count, which a required `note` then explains. After the swap the build refuses the flags themselves, naming the reading to write instead, and a particle with no given reading still states `may_be_given = false`, so a new particle cannot fall to the unsafe side silently.

`may_be_initial` is not derived. Its clash is with the initial, a shape reading every cased single letter has, and which letters a tradition writes both ways is a judgment about the letter, not a name anyone bears: `e` and `i` may be read as an initial in a name written in one case, `y` may not.

### One gate, four steps

Every clash is decided by one ordered question, asked at each site that reaches it today:

1. **Floor.** The name keeps a word to address: a title run gives its last word back ([rules/H3](rules/H3-title-runs-floor.md), the title run's floor), the second of two name words stays the family ([rules/S4](rules/S4-ambiguous-acronym-needs-words-to-spare.md), [rules/S10](rules/S10-trailing-roman-numeral.md)), and a bound given name keeps a family word in reserve ([rules/P5](rules/P5-bound-given-names.md)).
2. **Form.** A cue the reading's kind declares, read off the word's writing, settles the clash, and a clash settled by form is not reported.
3. **Structure.** The slot's own rule, in the order each slot reads it today: the ambiguous class at the comma ([rules/C4](rules/C4-ambiguous-credential-class-at-the-comma.md), the ambiguous credential class at the comma), the company of an unambiguous credential ([rules/S7](rules/S7-company-of-an-unambiguous-credential.md)), the credential's trailing run ([rules/S8](rules/S8-credentials-trailing-run.md)), a particle's leading position ([rules/P4](rules/P4-particle-at-the-front-of-the-name.md)), and the title phrase at the front of the name.
4. **Count.** Words to spare (S4, S10).

A clash not settled at step 2 is reported at the decision site (mechanisms.md#AMBIGUITY-AT-THE-DECISION-SITE), in the kind the slot reports today.

**Where one gate does not reproduce the six rules.** H3 and P5 weigh no second reading: they reach every member of their category and read only a count, so they stay floors, step 1, and "one gate for six" means four clashes and two floors. The ambiguous acronym is reached at nine sites, each reading its cues in its own order, and that order is behavior, so the nine sites stay; what becomes one is the predicate each asks (mechanisms.md#ONE-PREDICATE-PER-QUESTION). Everything else reproduces once the name readings are declared, except `ld`, whose name reading is moved into its credential reading's `note` so that it stays ungated.

### What each kind reads

| Reading kind | Clashes with | Form cues (step 2) | Then |
|---|---|---|---|
| credential, acronym | a name reading | its periods; capitals in a name of mixed case, asked of the whole name; Title case leans to the name; the joined (`MD/PhD`) and split (`Pharm. D.`) spellings | the comma count, the company, the run, the count |
| generation, whole word (`fils`) | a family reading | lower case in a name of mixed case settles the generation; Title case leans to the name | the count |
| generation, agnomen (`Filho`, `Neto`) | a family or given reading | none: an agnomen is written in the case of the name around it | the count |
| generation, roman numeral | the initial, for one letter; a name word | a period makes it an initial; lower case in a name of mixed case settles the generation; Title case leans to the name; an initial before it makes it a name word | the count |
| generation, initial-shaped (`H.` for *hijo*, regnal `I.`) | the initial | none: written with its period it is exactly an initial | no cue: `default = false`, for a pack |
| particle | a given reading | none: `Van` and `van` are both written | the leading position, the lone particle's fold |
| conjunction, one letter | the initial | the name's case ([rules/P8](rules/P8-single-letter-connective-against-the-initial-it-spells.md)); in one case, `may_be_initial` | — |
| title at the front | a given or family reading | none | the phrase partner, the title before it |
| bound given name | none (a floor) | — | — |

A reading whose writing offers no cue is one the gate could only guess, so it is `default = false`: recorded in the TOML, compiled to nothing by default, turned on by a pack in phase 3. Spanish `H.`, German regnal `I.` and Czech `st.` are the first.

**The numerals ask one predicate.** `i` to `v` are vocabulary and `vi` to `x` are shape, and until 2f some rules asked only the vocabulary, so `John Smith III MD` and `John Smith VI MD` read differently (#784, #774). One predicate answers for every spelling the way the trailing numeral rule does (shape, the count for one letter, an initial in front, the period, the case), and every rule that asks either recognizer asks it. Listing `vi` to `x` instead was measured and declined: a middle initial `X` would read as a generation.

**`fils` and the agnomens show what kind-specific cues buy.** `fils` is gated by its case and the count, so `Alexandre Dumas fils` reads suffix `fils` while `Marie Fils` keeps her family name, reported. The Brazilian agnomens are gated by the count alone: case would say nothing, and the plain generation reading breaks real surnames (`Ana Neto`) and given names. Phase 2h landed both on 2026-10-25, the floor holding before the case cue (`Dumas fils` keeps its family name, Derek) ([rules/S11](rules/S11-suffix-word-that-is-also-a-name.md), a suffix word that is also a name), with `default = false` for the three readings with no cue.

**A credential's spelling is a form cue.** A credential joined by `-` or `/` is to read as one when every chunk is listed and none is ambiguous, since a hyphen also joins names (`Smith-Jones`); an unlisted word of capitals joined that way is to join the ambiguous class after a comma, gated by the name's case contrast. `John Smith, MD/PhD` read given `MD/PhD` until phase 2c (2026-10-25) read the listed half: a joined word whose every chunk counts as a suffix as written ([rules/S3](rules/S3-credentials-written-in-joined-chunks.md)). A credential split across a space (`Pharm. D.`, generalizing the `Ph. D.` merge) is to merge only where its first chunk has two or more letters, the merged piece a member of the ambiguous class, decided by the comma count and words to spare: an opening single letter is a middle initial (`SMITH, JOHN A. MS.` holds an initial and a salutation, not a credential `AMS`). #872 made the same judgment for the joined spelling (`A.B.`), in scripts with capitals and outside the slot right after a comma. The merged piece is also to start the credential's run (#827), once the numeral predicate answers the numeral before a credential; since [rules/S8](rules/S8-credentials-trailing-run.md) refuses a member of the ambiguous class as a run start, how the two combine is the split-credential PR's to state (today's `Ph. D.` merge is unambiguous, and S8 already covers it). Phase 2e (2026-10-25) did both ([rules/S12](rules/S12-credential-split-across-a-space.md)): `John Smith, Pharm D` reads suffix `Pharm D`, and the split pair is the one member of the class that starts the run, behind the two name words its own count asks for.

### The front of the name

The front of a name has no words-to-spare cue: a title addresses the name after it. What it has is the contested-head rule. **A title word that also has a name reading is a title only inside a title phrase:**

- **The title before it is not a partner.** A contested word after another title is the given name (`Mr Sultan Khan`, `Ms Princess Ada Obi`, #853), unless that title is its partner; `Mr Sultan Khan` read title `Mr Sultan` until phase 2j gave `sultan` its given reading.
- **Its partner** is a modifier or a style before it (`Her Royal Highness Princess Anne`), `of` after it (`Dean of Students`), or a head title after it that the word `attaches` to (`Major General`). A salutation is never a partner (`SMITH, DEAN MR.` is a given name and a salutation).
- **Modifiers** (decision 10, unparked) are titles only beside a head title, at the head of the name only, never in a comma part, where a lone title word is the person's role; a modifier that is also a given name (`wing`, phase 2j) is read by that test in every part.

Phase 2i carried this out as [rules/H9](rules/H9-title-phrase.md) (the title phrase), with `of` after a modifier as a partner too (`Member of Parliament`) and a modifier in a connective's object (`President of the United States`); a title that may be a given name compiles out of `titles`, so one a caller lists there is a title everywhere. Which title words get a given reading is decided one word at a time (decision 16), in measured batches, and `Dean Smith` keeps reading given `Dean` (decision 13). A title that only ever stands in front stays a title (`lord`, `sir`, `lady`), and a word that opens names in one tradition but is a title class in another (`guru`, with its Devanagari twin) waits for a language pack. Where the rule reads a contested title as a name, the parse reports `title-or-name`.

**Abbreviated given names** use the same pool from the other side (#789): a `given` reading with `same_as` the full name (`chas` → Charles, Filipino `ma` → María) is to outrank the leading-abbreviation title rule's shape, so that `Ma. Cristina Santos Reyes` reads given `Ma.` where it read title `Ma.`. Phase 2k (2026-10-26) did this: the reading compiles into `GIVEN_NAME_ABBREVIATIONS`, which [rules/H2](rules/H2-leading-abbreviation-title.md)'s shape declines, and nothing else reads it.

### Brackets

A bracketed or quoted credential is to escape the nickname reading where its writing settles it (#810): with interior periods, or in capitals in a name of mixed case, the case asked of the whole name. `(Ed)` stays a nickname, and so does content standing inside the name rather than after it (`Jean 'JD' Smith`).

Phase 2l carried this out as [rules/S13](rules/S13-bracketed-member-settled-by-its-writing.md) (a bracketed member settled by its writing) rather than as an amendment to [rules/S1](rules/S1-bracketed-credential-is-not-a-nickname.md), since the position it reads is a signal S1 does not: `John Smith (MA)` and `John Smith (M.A)` read suffix, and `JOHN SMITH (MA)` and `Jeffrey (JD) Bricken` keep the nickname. The writing is read as the rules that read it say, S3 for the periods and S6 for the capitals in a name of mixed case, and S13's own signal is the position. A settled member is the suffix, decided in one pass, rather than the word read bare, since bare, `M.A` reads as initials; where the rest of the name then reads otherwise than beside a bracketed unambiguous credential (`Jack (MA)` keeps family 'Jack' where `Jack (PhD)` reads given 'Jack'), S13 records the difference as accepted.

### Readings on the parse

A caller should be able to see the reading behind a parse. **An `Ambiguity` carries the reading the parse did not take** (`Ambiguity.alternative`: its kind, the field it would have put the token in, and whether it came from the vocabulary, a declared name or a shape), and **a token carries the reading it did** (`Token.reading`), so a word whose reading forks nothing still says what it was read as, without a report nobody would act on (phase 4's 4a; a native spelling such as `do`'s Vietnamese `Đỗ` is not part of it). A word the credential's run takes by position alone is told from a word with a declared name reading by that source, so it needs no new ambiguity kind. `Ambiguity.alternative` shipped in 2.7 (decisions/A1, 2026-10-26 #752): a `Reading` of a kind, the field the word would land in with every other word read as the parse read it, and a source, which is `vocabulary`, `declared`, `shape` or `position`, the fourth being the reading of an ordinary word nothing lists, which is what a word the credential's run took by position alone has. The pickle guard was widened to accept a field added later. A `languages` field, naming the files that hold a reading, was weighed and left out: it needs the per-word reading index, which costs about 0.35 ms of an 18.2 ms import (decisions/A1) and could not describe a pack's or a caller's lexicon, so it waits with `Token.reading` for 3.0. Phase 4's 4a carried out `Token.reading` on 2026-10-29 (decisions/vocabulary-model's 2026-10-29 #754, sub-phase 4a entry), and its follow-up `Reading.languages` the same day, from phase 3's index (the 2026-10-29 #754, 4a's follow-up entry).

### The phase 1 reserved names

Phase 2 gives two of them meaning: `attaches`, the phrase partner above, a property of a title reading naming the title kinds it qualifies; and `default = false`, for readings with no cue. `leading_only` and `trailing_only` are not needed, the gate's slots carrying position; `bare_only` is settled by shape already ([rules/P7](rules/P7-one-letter-particle-against-the-initial-it-spells.md), a one-letter particle against the initial it spells); `separators` belongs with `attached` and its other side, phase 4's glued words. Those four stay reserved, their messages naming the phase that needs them.

## Phase 3: packs that prefer or restrict

Status: **agreed** (proposed 2026-10-27, #753; Derek accepted every item on 2026-10-28, six and then the other six); **3a landed 2026-10-29**, the reading index, the compiler moved into the package and `default = false` on name readings (decisions/vocabulary-model's 2026-10-29 entry, which records what 3a decided and measured, and the index's lazy load, which Derek chose on 2026-10-29 over loading it with `Lexicon.default()`; "Where the provenance lives at runtime" below describes it). **3b landed 2026-10-29**, the choice: `Locale.languages`, its tag selection, turning on, prefer and the shape clash of `may_be_initial`, the derived deviation surface, `snapshot.py --languages`, and mechanisms.md#LOCALE-PACKS-PURE-DATA amended (decisions/vocabulary-model's 2026-10-29 phase 3b entry, which records what it decided, measured and left open). **3c landed 2026-10-29**, the eight pack-shaped exclusions (cs `ml`, hr, sk and sl `st` and `ml`, fr `père`) written as `generation` readings `default = false`, the default's compile unchanged (decisions/vocabulary-model's 2026-10-29 phase 3c entry, which records what each choice now moves). The record is decisions/vocabulary-model's 2026-10-27 #753 entry; this section describes its items. One design inside the work order is still open: 3g's connective (below), which accepting the work order did not decide. Phase 3 is 3.0 work (re-planned 2026-10-28): 2.8 is the last 2.x feature release, and 3.0 ships phases 3 and 4 with the facade's removal. Packs stay opt-in, so a caller who chooses no language parses as the default does, and nothing in this phase moves the default's parses. One standing text is amended with it, in 3b's PR, which builds the selection: mechanisms.md#LOCALE-PACKS-PURE-DATA's contract that a pack is add-only and declares its deviations in its docstring (a pack adds, and selects among the default's readings by language, its deviations derived for a vocabulary pack). decisions/3-0-reevaluations' line that removing base vocabulary through a pack is part of 3.0's pack design is carried out rather than moved.

**Phase 4's shape questions came first.** The output model decides what a pack can express: a patronymic field, a second surname, credentials apart from generation suffixes (#326), and what `middle` means (#704). A pack reading of a kind with no field to land in is a reading nothing can surface, so those questions were to be settled before or with phase 3's mechanism, by the same shape-before-value rule, and the output model was agreed on 2026-10-28 (decisions/vocabulary-model's 2026-10-28 #754 entry): the seven roles stay, and `generation`, `credentials`, `patronymic` and `surname2` are views read from `Token.reading` or rules/O6's tag. Of the work order below, 3a (the reading index and the shared compiler) and 3c (the pack-shaped exclusions converted) are independent of the output model: the index carries whatever kinds the files hold, and 3c moves data between two encodings that compile alike. 3b's selection semantics are independent too, and its API's dependency, what `Locale` and `Policy` look like once the facade is gone, is answered (below). The packs depend on the output model in part, each on the phase 4 sub-phase that builds its view: `cs`'s generations and `pt-BR`'s agnomens on 4b's `generation` (3f and 3h), `es` and `pt` on 4d's `surname2` and 4g's compound given name (3g); `ne`'s readings do not.

The semantics were fixed in 2026-10-15/16, and phase 3 keeps them. A pack is a choice of languages, in two strengths (decision 6):

- **prefer** settles a clash where the chosen language has a vocabulary reading: the word keeps that language's readings and loses other languages' vocabulary readings. Under Portuguese, `do` is a particle only.
- **strict** also drops other languages' name readings. It is for single-origin data.

The asymmetry is deliberate (decision 15): **vocabulary readings settle a clash; name readings only keep the gate on.** `do` shows why. Its Vietnamese reading is a name only (Đỗ). If name readings settled clashes, preferring Vietnamese would drop the credential reading, and `John Smith DO`, a suffix today, would read `DO` as the family name. Under the rule, Vietnamese holds no vocabulary reading of `do`, so preferring it settles nothing: the credential and particle readings stay, gated as in the default.

Consequences that follow from the definitions:

- **Order does not matter.** A choice is a set of languages, so combining packs is commutative. Decided 2026-10-28 (below): strictness belongs to the whole choice rather than to one pack, reshaping decision 6's "strict variant", and strict waits until name readings say whose names they are.
- **Two chosen languages that each hold a vocabulary reading both keep it**, and the word stays gated, as in the default.
- **Non-Latin vocabulary stays on under any choice**, because it selects itself by script (`씨`, `さん`, Cyrillic titles). Almost every clash between languages is within one script: `do`, `e`, `van` are all Latin.
- **Whether a word needs a pack depends on where its clash is.** `do` clashes between languages, so a pack settles it. `fils` clashes within French, a generation word and a French surname, so no pack settles it and the phase 2 gate does the work, reversing the premise of #684.
- **A pack can outrank a shape rule, not only a vocabulary reading** (decision 20). Shape rules emit readings into the pool rather than final answers, so a pack's preference can act on them; phase 2k applied this in the default, a declared `given` reading of `Ma.` outranking the leading-abbreviation title.

What the inventory of the kept-out words found (#753's comments of 2026-10-27, 411 candidate readings) changes the emphasis rather than the semantics. Only 9 words clash between languages (`de`, `do`, `i`, `st`, `sr`, `ra`, `mc`, `vd`, `abd`), so prefer alone settles little; most pack candidates are readings the default leaves out entirely, which a pack turns ON. Phase 3's main work is therefore turning readings on, with prefer and strict settling what turning them on collides with.

### One mechanism: a choice selects the pool

Everything a pack does is one operation: **the chosen languages select which readings of the pool are compiled**, by the same compiler that builds the default. The default is that compiler run with every language and no choice. Nothing is written per pack beyond the readings in its language's file, and every effect below is derived from the file a reading sits in:

| Effect | Which readings | Example |
|---|---|---|
| turn on | a chosen language's `default = false` readings join the pool | cs `ml` (*mladší*, once 3c makes it a reading): `Jan Novák ml.` reads family `ml.` today; under `cs`, suffix `ml.` |
| prefer | on a word where a chosen language holds a vocabulary reading, other languages' vocabulary readings leave; `mul.toml`'s readings never do, being every language's | `Haddad, Abd` reads suffix `Abd` and no given name today; under `ar` the bound given reading stays and the en credential leaves; cs `st`: `Jiří Dienstbier st.` reads title `st.` today (rules/H5), and under `cs` its generation reading joins and the Saint readings leave, suffix `st.`, reported as suffix-or-name since en's `given` reading of `st` still gates it |
| prefer, against a shape | a clash a property records with a SHAPE reading is settled for the chosen language's own reading, by decision 20: `may_be_initial` does not hold on it | `ANA SILVA E SOUZA` reads middle `SILVA E` with a conjunction-or-initial report today; under `pt` the conjunction holds, family `SILVA E SOUZA` |
| strict, deferred (below) | other languages' name readings leave, and with them the markers they derive | an `nl` `in` turned on, with Korean In declared as a `given` reading, is a particle that may be given under `nl` and never-given under strict `nl` |

The third row answers decisions/3-0-reevaluations' "a pack cannot remove `e`": `may_be_initial` records a clash between a conjunction and the initial a letter spells, and the initial is a shape reading, so a pack that prefers Portuguese settles it, as decision 7 says choosing a language does and decision 20 permits. It reaches every reading the property stands on, pt and it `e` and ca and pl `i`, the Italian one unjudged by the inventory; and it forecloses the other direction of the 2026-08-18 bullet there, an `nl` pack marking `y` as an initial, which waits with the `fru` question below. Two parts of the mechanism are new beside decision 6: the exemption of `mul.toml` from prefer (under `ca`, `i` keeps its mul generation), and strictness as a property of the whole choice. No property is toggled per pack, and no reading is written twice.

Properties ride on their readings, so a choice that keeps a reading keeps its properties. The one shape this cannot express is a property a language's own reading should take only under its pack: Swedish `fru` and Icelandic `frú` as after-given salutations (rules/H8), refused in the default because Fru is also a Cameroonian surname. The inventory found two readings needing it (2026-10-27), so phase 3 builds nothing for them and leaves them open.

### Where the provenance lives at runtime

The compiled module holds sets, and a set has forgotten which file each word came from. Phase 3 compiles a second module beside it (decided 2026-10-28): a **reading index**, one row per reading (its text, its file's tag, its kind and its behavioral properties), loaded once per process on its first lookup (`_reading_index.readings_of`, and `languages_of`, which a parse calls) (decided 2026-10-29, replacing the 2026-10-28 decision to load it with `Lexicon.default()`). Phase 4's `Reading.languages` is filled from it at assemble (4a's follow-up, decisions/vocabulary-model's 2026-10-29 #754, 4a's follow-up entry), so the first parse in a process that reads a word from its `Lexicon`'s vocabulary loads it (a listed or declared word, a Korean surname dividing hangul or a caller's own word, whether or not a file holds it): every caller who parses such a name pays it once, about 1 ms on that parse with bytecode cached and about 16 ms without it, and a caller who only imports nameparser, or parses only words its `Lexicon` does not list, does not. Filling `reading.languages` on first access to that field instead was weighed and set aside: a `Reading` holds its kind, role and source but not its word, so a lazy field would have to carry the word as a hidden key on a frozen, slotted, pickled type, to save a cost the measurement below puts at about 2% of the import. The compiler moves from tools/vocab/build.py into the package so that the build and a pack share one implementation, and a test holds the invariant that compiling the index with no choice reproduces `nameparser/config/_compiled.py` exactly. The same index is what item 13 of decisions/vocabulary-model's 2026-10-23 #752 entry says `Token.reading` needs in 3.0; 3a built it (decisions/vocabulary-model, 2026-10-29), its import measured there at 0.56 to 0.68 ms.

Measured 2026-10-27 on `cfe8bf92`: the pool holds 2,140 readings over 1,797 words, 106 of them in more than one file. An index of their behavioral properties is about 93 KB of generated source. Imported with its bytecode cached, as an installed wheel has it, it takes about 0.45 ms (median of nine fresh processes, 2026-10-28 on `c8357e74`, Python 3.11.17), against about 20 ms for `import nameparser` cached the same way; with no cache it takes about 11 ms, the figure this section gave on 2026-10-27, measured in a shell that sets `PYTHONDONTWRITEBYTECODE`. That load is paid once per process, at the first lookup. Compiling the pool takes about 9 ms, paid once per choice and only by a caller who makes one. Reading the TOML instead costs about 39 ms. Recompute: the build's `read_dir`, `load` and `compile_pool`, timed; for the import, write the index as a module, `py_compile` it, and time its import in fresh processes beside a cached `import nameparser`.

Two cheaper-looking forms do not work. Per-language deltas compiled at build time do not compose: under prefer `{pt, en}`, `do` keeps both its particle and its credential, but Portuguese's delta removes the credential and English's removes the particle. And precompiling every combination of languages is combinatorial.

A choice is applied as a delta against the default's compile, so it composes with a caller's own `Lexicon`: `parser_for(locales.NE, base=Parser(lexicon=custom))` keeps a title the caller added, and a `Locale`'s own `lexicon` fragment is still unioned on after the choice. The delta removes what the choice drops whoever put it in the base: as built in 3b, `parser_for(EN, base=Parser(lexicon=Lexicon.empty().add(particles={'do', 'van'})))` keeps only `van`, since `en` drops `pt`'s particle `do`, the caller's listing of it included. And a choice is one call's (decided 2026-10-29, decisions/vocabulary-model's chained-choices entry): a `Parser` records no choice, so `parser_for(EN, base=parser_for(PT))` applies `en`'s after `pt`'s, reading `Maria do Carmo` family `Carmo` and `John Smith DO` family `DO`, and `parser_for(PT, EN)` is how both are chosen, keeping both readings. Whether a `Parser` records its choice, so that chained choices union, is decided with the configure-by-reading method names.

### The API and tags

This rested on `Locale` and `Policy` keeping their 2.x shape after the facade's removal, and the 2026-10-28 3.0 freeze answers it: both keep it, with additions. A choice is carried by `Locale`, which gains a `languages` field, a set of BCP 47 tags. `parser_for` unions the `languages` of the packs it is given, so the choice is order-independent while their policy patches still fold in order. Strict, once it can be built, is a property of the whole choice, not of one pack, and an argument: `parser_for(locales.NE, locales.HI, strict=True)`. The shipped language packs are `Locale` constants like the four today (`locales.NE`, `locales.get("ne")`), each with an empty lexicon fragment (what a fragment holds once 3.0 configures vocabulary by reading is decisions/vocabulary-model's the 2026-10-28 #754 entry on the `Lexicon` surface); a code keeps `Locale`'s `[a-z0-9_]+`, so `pt-BR` is `locales.PT_BR`.

A chosen tag selects its own file and its ancestors', never its descendants': `pt-BR` selects `pt-BR.toml` and `pt.toml`, and `pt` selects only `pt.toml`, so a caller in Portugal does not turn on the Brazilian agnomens (#843 left the single-letter `F` and `N` to a `pt-BR` pack). No macrolanguage table is read: Malay and Indonesian are separate tags, though BCP 47 counts Indonesian within the Malay macrolanguage, and a caller with names in both chooses both. The Czech, Slovak, Slovenian and Croatian files each hold the words they share, so each language is a pack of its own. Script subtags need no matching rule yet, since no file carries one.

The TOML names `prefer` and `strict`, reserved for phase 3 since phase 1, stay refused, with a message saying that a strength is the caller's choice and never data.

### Measuring a pack

`compare.py` parses under the default, so it cannot see a pack; `snapshot.py` can, taking a choice since 3b (`--languages`), which the third measure below uses (decisions/3-0-reevaluations, whose harness bullet this overtakes). Three measures, the first two in CI:

- **The default does not move.** The committed snapshot holds it, as for any change, and so does the index invariant above.
- **A pack moves only names holding a word it changes.** The words whose compiled readings a choice changes are computable from the index, so a vocabulary pack's deviation surface is derived rather than hand-copied, and the non-interference gate in tests/v2/test_locales.py runs every corpus name without such a word under the pack and requires the default's reading. The packs whose behavior is policy or segmentation (JA, RU, TR_AZ, ZH) keep their hand-written `DEVIATES`.
- **What a pack does, read by shape.** `snapshot.py` and `snapshot.py --local … --base <checkout>` take a choice of languages and print the names it moves, grouped by changed field, as they do for the default; each pack PR reads its own ground truth beside that: nepal-candidates' script pairs for `ne` (mechanisms.md#PAIRED-SPELLINGS-PER-CHANGE), the CLDR agreement per pack where CLDR has the language, the PSC register's nationality slice where filers of that language are many.

### Order is not shape

Decision 14 separates two things a "language" was going to carry:

- **Order** says which position holds which role. It is a small closed set (`GIVEN_FIRST`, `FAMILY_FIRST`, `FAMILY_FIRST_GIVEN_LAST`, plus the order a script implies) and a claim about how the data was written. A language supplies only a default (Hungarian and Vietnamese are family-first in Latin script), and the caller overrides it.
- **Shape** says where the non-name parts sit around the name: titles, suffixes, particles, commas. Shapes belong to an order, not to a language, so they live in the core.

CLDR's person-name data shows why. Its surname-first renderings put the title between the family and the given name more often than in any other position (counted 2026-10-16 in the CLDR corpus, across about fifty locales including `en`, `de` and `pt`), so it is a shape of `FAMILY_FIRST` everywhere, not a convention of some language. Today it is misread (measured 2026-10-19):

| Input under `FAMILY_FIRST` | Today |
|---|---|
| `Brühl Dr. Ada` | family `Brühl`, given `Dr.` |
| `Brühl Prof. Dr. Ada Cornelia` | family `Brühl`, given `Prof.`, middle `Dr. Ada Cornelia` |

The plan is to keep order a few permutations and make shapes first-class, each order accepting a listed set of them. The shape inventory (#469) is the start, and it doubles as the test grid that nameparser/AGENTS.md's comma-shape and `name_order` sweeps describe. The related comma bug, a title before a family comma, was fixed in 2.x ([rules/H6](rules/H6-title-before-a-family-comma.md), a title before a family comma).

### The rules a pack can choose

A language file will hold a `[rules]` table that turns on rules implemented in the core: a default order, patronymic and married-name endings, a surname span, a compound given name. A new rule kind is a core change with a mechanisms.md entry, never code in a pack; the one code hook stays the segmenter. The existing packs fit as 4f built them: RU's and TR_AZ's `[rules]` turn on their ending rules, the endings staying in the core with the rule kinds, and their deviations stay hand-copied, a test holding them to the rules each patch turns on; ZH and JA keep their hand-written segmentation patches (decisions/vocabulary-model's 2026-10-29 #754, sub-phase 4f entry, which reverses in part the 2026-10-27 #753 entry's item 10). Measured gaps each rule would close (2026-10-19):

| Rule | Input | Today |
|---|---|---|
| surname span | `Gabriel García Márquez` | middle `García`, family `Márquez` by default; family `García Márquez` under the opt-in `Policy(two_family_names=True)` |
| compound given name (pt) | `Maria do Carmo Silva` | given `Maria`, family `do Carmo Silva` |
| married-name ending (hu) | `Kovács Jánosné` | given `Kovács`, family `Jánosné` |
| digraph initials (cs) | `Petr Chmelař` | initials `P. C.` |

The surname span has shipped ahead of the packs, as an opt-in `Policy` field rather than a pack, since the convention is not one language's ([rules/O6](rules/O6-two-family-names.md), two family names, #875 and #878; decisions/O6 has why it is not `locales.ES`). A pack can later switch it on in its `[rules]`, as it will a default order.

**A language file's `[rules]` compiles into its shipped `Locale`'s `policy` patch**, at build time as the vocabulary does, so a rule a pack turns on is a `Policy` field (`two_family_names`, `patronymic_rules`, and the new rule kinds as new fields) and `Locale` gains no field for rules. RU and TR_AZ become that: their `PolicyPatch` compiled from `ru.toml`'s and `tr.toml`'s `[rules]` instead of written by hand. Built in 4f: the build writes each file's table as tuples in `nameparser/config/_rules.py`, which `_locale.rules_patch` builds into the pack's patch when the pack is imported; each key is the `Policy` field of its name, a file turns a rule on and never supplies what it matches, and `DEVIATES` stays hand-written, held by a test to the rules the patch turns on (decisions/vocabulary-model's 2026-10-29 sub-phase 4f entry; `nameparser/vocab/README.md`'s "Rules" has the keys). The compound given name is measured in the fielded corpora: in ORCID and PatentsView records from Brazil, Portugal, Spain, Mexico, Argentina, Colombia, Chile and Italy whose given-names box holds three or more words with a particle inside (the `Maria do Carmo` shape) and whose family box is filled, 1,812 of 1,923 ORCID records and 1,165 of 1,219 PatentsView records read with the given box's words pulled into the family (2026-10-28, master `c8357e74`). Like the surname span, it is a rule a caller or a pack turns on, since `Juan de la Vega` is the same string shape with the opposite answer.

The real-name corpora agree on the priority. In the GND and Wikidata corpora, Spanish and Latin American double surnames written given-first disagreed with the source on 315 of 390 names, while the same kind of names in index form, where the comma settles it, disagreed on 0 of 60 (counted 2026-10-16 on master `4375b01b`, from `gnd_agreement.json` and `wikidata_agreement.json`): the gap is order and span, not vocabulary. The PSC register ranks it (#754's comment of 2026-10-23): 22,168 of its 1,040,708 filed names read a two-word surname's first word as a middle name, the largest disagreement shape in its score.

### The output model

Phase 4 also decides what a parse returns, aligned with CLDR's person-name fields, which gives ground truth for free. Five things were asked for: a second surname (`surname2`), a patronymic (decision 8), credentials apart from generations (#326), a meaning for `middle` when a given name is several words (#704), and the reading each token took (`Token.reading`, phase 2's item 13). The first four are fields, and the design answers them with one shape; the fifth is what most of them are read from.

**The seven roles stay, and every new field is a view.** A `Role` partitions the tokens: each word is in exactly one of title, given, middle, family, suffix, nickname and maiden. Each field asked for subdivides a role that exists, not to add a part a name has outside them: a second surname is part of the family, generation and credentials are parts of the suffix, a second given name is the middle, and a patronymic is a word the parse already puts in the family (Icelandic, Arabic and Malay names) or in the middle (East Slavic names). So each is a view computed from the tokens, as `family_base`, `family_particles`, `surnames` and `given_names` are today (rules/R1, rules/R2), except the second given name, which is the `middle` that exists (below): a property and a render key, with `as_dict()`, `comparison_key()` and the seven role properties unchanged. Every view is an addition under the 3.0 freeze. A new `Role` member would not be: `as_dict()` would gain a key, `comparison_key()` a component (a stored key would stop matching), `for role in Role` a member, and the role a token moves out of would return less text than it does in 2.x, a change in what `family` or `suffix` means that no 2.x warning has announced.

What decides a view is the reading each token took, so `Token.reading` comes first; `surname2` alone is read from a mark O6 leaves, a rule rather than a word deciding it, which the reading carries out (`Reading.second_surname`, decisions/R10):

- **`Token.reading`**: a `Token` field holding the `Reading` the parse took, the same type `Ambiguity.alternative` holds the reading not taken in (decisions/A1), `None` for a token `replace()` or `revise()` builds. Its `kind` says what the word was read as, its `source` why, and a `languages` field, added to `Reading`, names the language files holding that reading, filled from phase 3's reading index (3a) and left empty for a reading no file holds (a word a caller's own `Lexicon` adds that no file holds in that category, a shape, position alone, and the Korean surname list, which stays outside the per-word files); it too takes `ADDED_IN` and is not compared, `Reading` having shipped in 2.7. The field takes `ADDED_IN` metadata, so a 2.x pickle loads with `None` (the pickle guard as widened in 2.7), and is left out of comparison (`compare=False`), so `==` between two `ParsedName`s means what it means in 2.x. `ReadingKind` gains `PATRONYMIC`, its docstring already allowing new kinds.
- **Generation and credentials** (#326): `generation`, the suffix tokens whose reading is a generation or an agnomen (`Jr.`, `III`, `Filho`), and `credentials`, the rest of the suffix (`PhD`, `Esq.`, the honorifics after a name), so the two partition `suffix` and `suffix` is unchanged. CLDR has only these two buckets; the post-nominals that are neither (`Esq.`, the CJK and Hebrew honorifics, `Rinpoche`) fall in `credentials`, CLDR's catch-all, and a caller who wants them apart reads `Token.reading.kind`, which says `post-nominal`. Measured 2026-10-28 on `c8357e74`, over the committed corpus's 6,533 distinct entries (`snapshot.corpus_entries()`) each parsed under its declared order: of the 1,054 with a suffix, 33 hold a generation (or agnomen) and a listed credential together, 77 a generation beside any other suffix word, and 64 only listed post-nominals of other kinds. Of the 615 CLDR renderings with a generation or credentials field, 75 parse with exactly CLDR's suffix words, and in all 75 a split by the vocabulary's reading kind gives CLDR's `generation` and `credentials` both; the other 540 differ in which words the suffix holds, a parse question the split cannot fix. Recompute: classify each suffix word (a token tagged `joined` merged into the one before it) by the kinds of its suffix readings in nameparser/vocab/, matched lowercased with its periods and spaces removed, skipping `default = false` readings, a generation or agnomen reading winning over a credential and a credential over the other kinds, an unlisted roman numeral `i` to `x` a generation and any other unlisted word unlisted; over the corpus entries above, and over `cldr_fields.jsonl` for CLDR.
- **A patronymic** (decision 8): `patronymic`, the tokens whose reading is `PATRONYMIC`, in whichever role the parse put them, with `family` and `middle` unchanged. What fills it is a word or a rule that says patronymic, never a guess from position: the vocabulary's `patronymic` particles (`bin`, `binti`, `ibn`, `bint`, Hebrew `bar` and `bat` and the native-script forms) with the name after them, in the default, so `Mahathir bin Mohamad` reads family `bin Mohamad` as today and patronymic `bin Mohamad` beside it; the East Slavic and Turkic rules where RU or TR_AZ turns them on, so `Ivan Ivanovich Ivanov` under RU keeps middle `Ivanovich` and adds patronymic `Ivanovich`; and an Icelandic ending rule an `is` pack would turn on, the default unable to tell `Karlsdóttir` from the Swedish surname `Johansson`. The name `patronymic` is kept for a matronymic too, which is written the same way and cannot be told from one. **`family` is not emptied** by recognizing a patronymic, revising what this section said before: the people filling in the fielded corpora put the patronymic in the family box (below), as CLDR's samples put an Icelandic patronymic in `surname` or `surname-core` (CLDR's `is` file's 3 Icelandic samples, in all 9 of their renderings; its one foreign sample puts a `-dóttir` word in `surname2`) and a Russian one in `given2` (its 2 `ru` samples, in all 6 renderings), our `middle`, while Wikidata records an Icelandic name as a patronymic with no family name; a `family` that keeps it and a `patronymic` that names it satisfy both. A caller writing "Mr. {family}" reads `patronymic` to see that the family is one.
- **A second surname**: `surname2`, the family's second name unit where a rule has read the family as two (rules/O6, which a caller or an `es` pack turns on), and empty otherwise, `family` keeping both units as O6 makes it today. O6 already knows which unit it took, so it marks the second one's words, a private tag that the published reading carries as `Reading.second_surname` (a stable tag, as first written here, would make an O6 parse unequal to its 2.x pickle, `Token` comparing its tags; decisions/R10); a family comma alone marks nothing, since `Lloyd Webber, Andrew` is not two surnames, and a hyphenated family is one token and stays whole. Whether the first unit gets a view of its own, and its name (`surname` sits close to the `surnames` that exists), is a value question below. `surnames` keeps its meaning, `middle` and `family` joined, the reading of a double surname the default splits.
- **`middle`** (#704): keeps its meaning, every word of the given part after the given name, and the given name is one name unit unless a rule joins words into it, as rules/P5 already does (`Abdul Aziz Tariq` → given `Abdul Aziz`). A compound given name (`Maria do Carmo`, `María José`) is the `[rules]` rule above, turned on by a caller or a pack, moving its words into `given` only under that rule. CLDR's `given2` is `middle`, so no view is added. A Sikh `Kaur` stays in `middle`, and so, under FAMILY_FIRST, does an English name written after a Chinese one (`Lim Mei Ling Jessica` → given `Mei`, middle `Ling Jessica`), an accepted cost.

**Render defaults** (decisions/3-0-reevaluations' render line, which this decides). The default `str()` reads every name given-first and joins its words with spaces, so a name read family-first is turned round and a written separator is lost: `str(parse("김민준"))` is `'민준 김'`, `str(parse("王 小明"))` is `'小明 王'` and `str(parse("威廉·莎士比亚"))` is `'威廉 莎士比亚'`. Over the committed corpus's distinct entries, each under its declared order (2026-10-28, `c8357e74`), 728 without a comma read family-first (the family's first word written before the given name's), `str()` renders every one differently from the text, and in 150 of them the family's last word touches the given name's first, written unspaced; of 41 holding the U+00B7 interpunct, `str()` drops it from 36. So:

- `ParsedName` gains `order`, the order the name was read under (its script's or the declared `name_order`, a family comma aside), an addition with `ADDED_IN` metadata whose missing value, in a 2.x pickle, renders as today, and left out of comparison as `Token.reading` is, so a loaded 2.x pickle still equals a fresh parse of its text. The cost, accepted 2026-10-28: two equal names can render differently, where today every rendering is derived from what `==` compares (a 2.x pickle of `김민준` renders `'민준 김'` and a fresh parse `'김민준'`, and a set keeps one of them); the views read from `Token.reading` share it.
- `str()` and `render()`'s default spec put the family first where `order` does, and two words that stand one directly after the other, in the same order, in the original and in the rendering keep the kind of separator that stood between them in the original, written in a normalized form (decided 2026-10-28): nothing stays nothing; whitespace of any width or length becomes one ASCII space, the ideographic space U+3000 included (decided 2026-10-28: `山田　太郎` renders `'山田 太郎'`, the same ASCII space `str()` joins with today, where today's order gives `'太郎 山田'`, and a caller wanting native spacing passes a format spec of their own or reads `ParsedName.original`); an interpunct or a nakaguro the parse read as a separator stands alone, with no space around it (an interpunct written with spaces round it is not one, rules/T3 dividing at it only when flanked, so `威廉 · 莎士比亚` reads the dot as a name word and keeps rendering with its spaces, where `威廉·莎士比亚` keeps the dot unspaced; a spaced nakaguro is a separator, so `ジョン ・ スミス` renders `'ジョン・スミス'`); and one comma the parse reads as one becomes `, ` if ASCII and `، ` if Arabic (U+060C), no space before it and one after, and stands alone if full-width (U+FF0C), which carries its own width in CJK text, a reason that holds for the comma, a mark the rendering keeps, and not for whitespace, which the rendering normalizes, so `John Smith ,Jr.` and `John Smith,  Jr.` render `'John Smith, Jr.'` and `John Smith， Jr.` renders `'John Smith，Jr.'`. The Japanese comma 、 (U+3001) is not one the parse reads as a comma, a parser question outside this design. Over that, the spec's decoration between the two fields the words belong to stands in place of the separator (the nickname's quotes, the `) ` after the maiden name, so `Jane Smith née Jones, PhD` keeps `'Jane Smith (Jones) PhD'`; 38 committed entries put a suffix directly after an undelimited maiden name); and any other pair, or any other separator (a delimiter, a marker word the parse consumed, two or more commas, a hyphen, a slash, a zero-width or directional mark), takes the spec's own joiner, as today (the written whitespace is not lost: `ParsedName.original` and the token spans keep it), so `John (Jack) Smith` keeps today's quoted nickname and `str(parse("김민준"))` is `'김민준'` and `str(parse("威廉·莎士比亚"))` keeps the dot. A name with a family comma or written given-first keeps today's word order, and its separators are kept by the same rule (a comma before a suffix alone does not make a family-first name given-first: `Wang Xiaoming, Jr.` under FAMILY_FIRST renders `'Wang Xiaoming, Jr.'`), so the given-first transcription `威廉·莎士比亚` keeps its dot too (20 of the 36 names whose interpunct `str()` drops are read given-first, 4 of them with a comma the parse reads (1 ASCII, 3 full-width)). A family comma is never kept, since the rendering reverses the pair it stands between (`Smith, John` → `'John Smith'`), while a comma directly between the family and its suffix is (`John Smith, Jr.` → `'John Smith, Jr.'`, where `str()` gives `'John Smith Jr.'` today): of the 1,003 committed corpus entries whose suffix starts after the family's last word ends, 214 have nothing between the two but one comma and whitespace (2026-10-28, `c8357e74`, each entry under its declared order; these counts read the ASCII comma, and 7 more write a full-width one there, while 36 of the 728 family-first names above hold a family comma the parse reads, 5 full-width and 31 Arabic (30 of the Arabic in `corpus_cldr.jsonl`), and so keep today's word order under the rule); 456 hold a comma somewhere between, most with a given name or title standing there too. Pairs the rendering separates, as `John` and `Jr.` in `Smith, John, Jr.`, take the spec's own joiner, as today, so `Smith, John, Jr.` keeps rendering `'John Smith Jr.'` while `John Smith, Jr.` becomes `'John Smith, Jr.'`: two writings of one name rendering differently, a consequence of following the text accepted with the choice.
- **How, decided 2026-10-28.** Today `str(name)` is `name.render()`, whose default is one fixed given-first spec, `'{title} {given} "{nickname}" {middle} {family} ({maiden}) {suffix}'`, which is why `김민준` renders `'민준 김'`; a default that reads `order` and the written separators cannot stay one string. So `render(spec: str | None = None)`: `None`, what `str()` passes, is the order-aware default, and a spec a caller writes renders exactly as written, its order and its literal joiners, with no separator rule applied, so `render("{given} {family}")` means in 3.0 what it meant in 2.x. That is a signature change, not an addition as the freeze defines one (decisions/3-0-reevaluations, THE CORE API), and Derek took it on 2026-10-28, waiving the 2.x warning the freeze asks of a break (decisions/3-0-reevaluations, THE RENDER SIGNATURE): no call that works today changes meaning, since `render(None)` raises `TypeError` today, but introspecting the default gives `None` rather than a spec, and a subclass overriding `render(self, spec: str = ...)` becomes an incompatible override to a type checker. The default's layout is picked by `order`, and a name with a family comma has a given-first `order` ("a family comma aside", above), so a given-first name and a family-comma name render by today's spec with the separator rule (`Smith, John` under FAMILY_FIRST still renders `'John Smith'`). For a family-first `order` the layout puts the title first and the suffix last, as the given-first spec does, and the three name roles between them in `order`'s own sequence, each keeping its decoration beside it: `'{title} {family} ({maiden}) {given} "{nickname}" {middle} {suffix}'` for FAMILY_FIRST and `'{title} {family} ({maiden}) {middle} {given} "{nickname}" {suffix}'` for FAMILY_FIRST_GIVEN_LAST, the separator rule then joining adjacent words (`王小明先生`, read family `王小明` and suffix `先生`, renders `'王小明先生'` where today gives `'王小明 先生'`; `Dr. Wang Xiaoming Jr.` under FAMILY_FIRST renders `'Dr. Wang Xiaoming Jr.'` where today gives `'Dr. Xiaoming Wang Jr.'`). CLDR's surnameFirst samples (`tools/differential/cldr_fields.jsonl`, release 48) agree on the core order and not on the rest: `ja` (`佐藤グレース恵子さん`) and `vi` (`ĐBQH Nguyễn Văn Anh`) put the second given name before the first, as FAMILY_FIRST_GIVEN_LAST does, and `ko` (`김민규헨리`) puts it after, as FAMILY_FIRST does; but most put the title after the family, not first: `pt` after it (`da Silva Sr. José Pedro Eduardo Jr., MP`), `ja` and `zh` last, and over every file's nativeFull surnameFirst rendering holding a title and a surname, 50 of 70 put the title after the surname (2026-10-28, positions of the field values in the text); `zh` also puts the generation first (`小彭德威东升议员先生`), and `vi` the credentials first. Keeping the title first, where the given-first default and the written name have it, goes against most of CLDR, but it is the one place the parse reads every title back from under a family-first order: `Senator Wang Xiaoming` reads title `Senator`, while `Wang Dr Xiaoming` reads given `Dr` and `Wang Xiaoming Senator` middle `Senator`, a bare title ending a name being a name word (rules/H5), only a period-marked one (`Wang Xiaoming Dr.`) reading as the title there (2026-10-28, under `Policy(name_order=FAMILY_FIRST)`). Derek decided on 2026-10-28 that the default renders only an order the parse reads back, so the title stays first; reading a title where CLDR writes it is the parser's question, #938, and the default may follow once the parse reads it there. A locale's own placement is the render patterns' job (below). The suffix last agrees with `ja` and `zh`, whose honorifics the parse reads as suffixes. For 3.0's notes: a caller who copied 2.x's default string and passes it keeps given-first, space-joined output; only a caller who passes nothing, `str()` included, gets the new default. `None` leaves both answers to how a pack's pattern is reached as open as they were: a spec string still means a spec, so `render("sorting")` still returns `'sorting'`, and a pattern is asked for by a new method or argument under (a) or through the parser under (b).
- `initials()` gives nothing for a word in a script with no initials (Han, Hangul, kana, `_policy._NO_INITIALS`), where today it gives the first character with a period (`'王.'`).

Apart from that signature, these change no signature but change `str()`'s output for every name read family-first, every name whose words are written with nothing, an interpunct or a nakaguro between two words the rendering keeps side by side (not `김, 민준씨`, whose family comma moves `김` between `민준` and `씨`), and every name written with one comma directly between its family and its suffix, which no 2.x release can warn about; Derek took them as an improvement for 3.0's release notes rather than a break (item 6 of the entry).

**Render patterns a pack may carry** (a shape agreed 2026-10-28; the feature is later work and an addition, in 3.0 if time allows and in 3.x otherwise). A `Locale` is a code, a `Lexicon` and a `PolicyPatch`; it may also carry named render patterns in CLDR's person-name shape (Unicode TR35 part 8, https://www.unicode.org/reports/tr35/tr35-personNames.html), a given-first and a surname-first display pattern and a sorting pattern, so a caller gets a region's standard forms without knowing its convention. CLDR is where a pattern starts, not its authority. In `tools/differential/cldr_fields.jsonl` (CLDR release 48), `pt`'s sorting pattern files its native sample under the FIRST surname, its particle after the given names, and leaves `surname2` out (`Silva, José Pedro Eduardo da`, `surname2` 'Silveira'), which is CLDR's two-surname model and not ABNT's last-surname entry (decisions/R2's 2026-10-28 #754 entry); `es`'s sorting pattern keeps its foreign sample's `von` in front (`von Miller Jones, …`), where RAE's rule (a) sets a Spanish preposition after the given name, and its native sample holds no particle, so it cannot show rule (a) either way.

What a pattern needs from this phase is the one gap the table shows: CLDR's prefix and core belong to the FIRST surname, while `family_particles` and `family_base` read the whole family, so filling them per surname needs the units told apart, each with its own particles and base. That is the first unit's view and the per-surname units the sort-key question under Left open reads, so they are one piece of work; CLDR has no prefix field for `surname2`.

A sorting rendering is not a sort key: it is a string, and a string sorts by code point, so accents, `ñ` and case fall out of order. Proposed, not decided: a key method beside `comparison_key()` returning a convention's fields in its sort order, each casefolded, which a caller hands to real collation (ICU, `locale.strxfrm`) for anything past code-point order.

How a call reaches a pack's pattern is open, and each answer costs something: `ParsedName` does not know the locale it was parsed under. (a) The parse records the convention on the name, as it records `order`, so a call on the name alone finds it: one more `ADDED_IN` field, and a new method or argument to ask for a pattern by, since `render()` takes a format spec today and `render("sorting")` returns `'sorting'`, so giving that argument a pattern's name would change behavior rather than add it; the field is missing on a 2.x pickle and kept out of `==` as `order` is, with the cost accepted for `order` (two equal names rendering differently). (b) Pattern rendering goes through the parser, `Parser.render(name, "sorting")` or the like, as `Parser.capitalized` does for a convenience that depends on configuration: no field and no pickle question, but a name alone cannot give its convention's forms. The render default decided above forecloses neither: `str()` follows `order` and reads no pattern, and under both answers a pattern is something a caller asks for.

**Gender**, recorded only where a word gives a definitive clue (decision 9), is not part of this design: the vocabulary records it on readings (`bint`'s `gender = "f"`), and `Token.reading` could carry it later as one more addition.

**Interleaved with phase 3** (its sub-phases 3a to 3i, above): 4a can start beside 3a, its `languages` waiting for 3a's index; 4d needs nothing of phase 3, and 4b and 4c need 3a's index only for a listed word's kind, a suffix word's and a particle's; they unblock its packs, `cs`'s generations (3f) and `pt-BR`'s agnomens (3h) on 4b, `es` and `pt` (3g) on 4d and 4g; 4f lands with or after 3b, since both decide what a shipped `Locale` holds; an `is` pack, which no phase 3 sub-phase lists, needs 3b, 4c and 4f. 3i, the bearers' languages strict would read, needs 3a alone, and 4e and 4h stand apart from both. So the order is 3a and 4a, then 4b to 4d with 3b and 3c (4b after 3a), then 4f, then the packs with 4g, with 4e at any point and 3i at any point after 3a.

**Left open.** With no sub-phase yet: phase 1's four reserved names said to be phase 4's (`separators` with phase 4's glued words, and `bare_only`, `leading_only` and `trailing_only`, which this RFC's phase 2 section found not needed), whose build messages still name this phase. The first unit's view of a family read as two, and its name, with each unit's particles and base, which CLDR's `surname-prefix` and `surname-core` and a sort key per surname would read: 4d built `surname2` alone (decisions/R10's Open).

A shape question, decided 2026-10-28:

- **Whether `Lexicon` keeps a public field for each compiled set**, or answers word, kind and property queries from phase 3's reading index and keeps its sets internal. `dataclasses.fields(Lexicon)` gives 22 public fields on 2026-10-28, 11 of them added since 2.0.0's 11 (`surnames`, `honorific_tails`, `conjunctions_ambiguous`, `after_given_titles`, `suffix_words_ambiguous`, `agnomens`, `given_name_abbreviations`, `titles_ambiguous`, `title_modifiers`, `title_styles`, `title_phrases`), each a new parse behavior's set, and a rule keyed on a title kind or on one language's reading of a kind (phase 3's design, "a property a language's own reading should take only under its pack") would add more. Keeping the fields: each is frozen API, shown in the bounded repr (`Lexicon(default + titles: +1)`), and pickled, where `Lexicon`'s own `__setstate__`, unlike the `ADDED_IN` guard the other types share, refuses any pickle whose fields differ, so every new field breaks every older `Lexicon` pickle, and with it every pickled `Parser` and locale pack, until that guard learns the marker. Turning them internal: a break that has to land in 3.0, where a query added beside the fields is an addition that can come later; a caller who configures vocabulary by the field today (`Lexicon.add(titles=...)`, `dataclasses.replace`) needs another way in, for words that carry no kind and no language; and phase 3's reading index, which a `Lexicon` answering queries would read, is loaded on its first lookup (decided lazy on 2026-10-29 rather than loaded with `Lexicon.default()`; about 0.6 ms with its bytecode cached, by phase 3's timing above). Since 4a's follow-up filled `Reading.languages` (2026-10-29), the first parse that reads a word from its `Lexicon`'s vocabulary makes one, so answering queries from it adds no load beyond that first lookup. The parser need not pay either way: a frozenset test per word costs no frame and an internal cache keeps that path, while a query method called per word would add one per token, the cost the frame budget counts as scaling with the input. **Derek decided on 2026-10-28 that a caller configures vocabulary by reading and the compiled sets become internal** (decisions/vocabulary-model's 2026-10-28 #754 entry on the `Lexicon` surface). A caller states what a word may be in the language files' terms, a `given` reading on `guru`, no credential reading on `dc`, and `Lexicon` derives the sets and gates the build derives, so making `Guru` a possible given name needs no knowledge of rules/H9's sets, where today it is `remove(titles={'guru'}).add(titles_ambiguous={'guru'})`, and `add(given_name_titles=...)` or `add(suffix_acronyms_ambiguous=...)`, the plausible wrong guesses, do something else. A reading is also what a caller can know about a word and what a pack contribution states. Removing a reading from a caller's own lexicon may settle a clash; decision 15 binds the default and the packs, not a caller's choice about their own data. It breaks the frozen `Lexicon` (decisions/3-0-reevaluations); the method names and whether a caller's own language file can join the pool later (phase 3 defers it) are open, and the 2.x warning the freeze asks for was waived on 2026-10-29, no 2.x feature release being left to carry it (decisions/3-0-reevaluations, THE LEXICON WARNING).

Value questions inside the shapes above:

- The first surname's view and its name, with its own particles and base (the gap the render-pattern table shows).
- How a pack's render pattern is reached, and the key method (Render patterns, above).
- Whether a language pack supplies a convention's entry element or sort key, built from the per-surname units this phase reads, `family_base` being the family without its working particles under every convention (an all-particle part's words staying, rules/R2's Except; decisions/R2's 2026-10-28 #754 entry). A `pt` or `pt-BR` pack would give the last surname's base first, keeping `Filho`, `Neto` and `Júnior` with it and a compound surname whole, and an `es` pack the first surname without its particle, then the second with its own (RAE's rules (a) and (e)).
- Whether a token's title kind reaches callers. A title token's tags name only behaviors (`Dr. Mr. Sir John Smith` gives `Dr.` `vocab:title`, `Mr.` `vocab:after-given-title` and `vocab:title`, `Sir` `vocab:given-title` and `vocab:title`); `Lexicon` splits the titles into `titles` and `titles_ambiguous` by whether a word is also a name, not by kind, and only `title_modifiers` and `title_styles` are sets of a kind; the salutation, academic, religious, nobility, military, office, occupation and kinship kinds live only in the TOML; and `ReadingKind`, being "the parse's, not the vocabulary's", reads every one as `TITLE` in `Token.reading` (since 4a), where the suffix readings split four ways. Phase 3's design already gives its reading index "its kind" per row ("Where the provenance lives at runtime", above), and a title reading is keyed by its kind in the TOML (`religious`, `academic`), so that row's kind is the vocabulary's by construction; what stays open is whether `Reading` gains an optional field exposing it, filled only where the reading's source is the vocabulary: a title read by its shape (`Insp.`) or a word a caller added by `Lexicon.add` has none, so its absence means unknown, not that the word has none. It is an addition and blocks nothing in 3.0, and it would let a view name the salutation alone (`Dear Mr. Smith`), which CLDR's one `title` field does not model. Whether it holds one kind or a set is part of the question: of the 816 title words in nameparser/vocab/ on 2026-10-28 none carries two title kinds, `father` being `religious` only, the README's "kinship word used as one".
- Whether `credentials` should leave the honorifics out, CLDR having no third bucket.
- Which ending rules beside Icelandic a pack may name (Hungarian `-né` is a married name, not a patronymic).
- The names of given names only (the last table row), whose reading needs a rule that tells a mononym from a given name and a family name, not an output field.
